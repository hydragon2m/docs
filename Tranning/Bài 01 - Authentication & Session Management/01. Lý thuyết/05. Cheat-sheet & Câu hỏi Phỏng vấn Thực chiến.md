## I. BẢNG TỔNG HỢP NHANH (QUICK REFERENCE CHEAT-SHEET)

| Câu hỏi thường gặp | Giải thích ngắn gọn & chuẩn xác |
| :--- | :--- |
| **Tại sao không lưu JWT vào `localStorage`?** | `localStorage` hoàn toàn có thể bị đọc bởi bất kỳ đoạn mã JavaScript nào chạy trên website. Nếu web dính lỗi XSS (do cài thư viện npm bên thứ ba có mã độc hoặc dính injection), token sẽ bị gửi về server hacker ngay lập tức. |
| **Tại sao dùng Cookie `HttpOnly` lại an toàn trước XSS?** | Vì trình duyệt áp đặt lệnh cấm JavaScript truy cập vào cookie đó. Lệnh `document.cookie` hoàn toàn "mù" với cookie `HttpOnly`. |
| **Dùng Cookie có nguy cơ bị tấn công CSRF không?** | Có, nếu cấu hình mặc định lỏng lẻo. Nhưng nếu đặt cờ **`SameSite=Lax` hoặc `Strict`**, trình duyệt sẽ từ chối gửi cookie trong các truy vấn cross-site từ website khác sang, triệt tiêu nguy cơ CSRF. |
| **Tại sao không kiểm tra Redis trong Access Token?** | Vì nếu mỗi request API đều phải chọc vào Redis thì JWT mất đi toàn bộ ưu thế của kiến trúc Stateless! Access Token phải thuần túy verify qua CPU Signature để đạt tốc độ dưới 1 mili-giây. Chỉ có Refresh Token (vốn chỉ gọi 15 phút một lần) mới cần kiểm tra Redis. |
| **Tại sao dùng Whitelist trong Redis mà không dùng Blacklist?** | Blacklist chỉ lưu token đã hủy; kích thước blacklist sẽ ngày càng phình to theo thời gian và không thể phát hiện được hành vi Replay Attack (tái sử dụng token cũ). Whitelist chỉ lưu các phiên hợp lệ đang online nên cực kỳ nhỏ gọn và hỗ trợ hoàn hảo Token Rotation. |

## II. BỘ CÂU HỎI PHỎNG VẤN THỰC CHIẾN (SENIOR / LEAD INTERVIEW QUESTIONS)

### Câu 1: *Làm thế nào để vô hiệu hóa một JWT trước khi nó hết hạn?*
* **Trả lời chuẩn:**
  Về mặt lý thuyết, JWT thuần túy là stateless nên không thể vô hiệu hóa cục bộ trên server. Để giải quyết bài toán này trong thực tế, chúng ta có 3 cách:
  1. **Cách 1 (Chuẩn Production):** Sử dụng kiến trúc Dual Token. Access Token có TTL siêu ngắn (10-15 phút), còn Refresh Token được gắn mã `jti` (JWT ID) và kiểm soát qua Redis Whitelist. Muốn hủy phiên chỉ cần xóa `jti` trong Redis ($O(1)$).
  2. **Cách 2 (Blacklist):** Lưu `jti` của các token bị logout vào Redis với TTL bằng thời gian sống còn lại của token đó. Nhược điểm: Phải query Redis trên mọi request.
  3. **Cách 3 (Token Version):** Lưu một trường `tokenVersion: number` trong bảng User ở DB. Khi user đổi mật khẩu, tăng `tokenVersion` lên 1. Mọi token mang `tokenVersion` cũ đều bị Guard từ chối.

---

### Câu 2: *Giải thích cơ chế Silent Refresh ở Frontend (Next.js/React)?*
* **Trả lời chuẩn:**
  Silent Refresh là kỹ thuật tự động làm mới Access Token ngầm dưới nền mà không gián đoạn trải nghiệm của người dùng:
  - Frontend sử dụng một Fetch Interceptor (như Axios Interceptor hoặc Fetch Wrapper).
  - Khi một API trả về HTTP `401 Unauthorized` (do Access Token hết hạn), Interceptor sẽ tạm dừng (pause) các request tiếp theo và đẩy vào một hàng đợi chờ (Queue).
  - Interceptor gửi request `POST /auth/refresh` (trình duyệt tự đính kèm Refresh Token trong `HttpOnly Cookie`).
  - Khi Backend trả về Access Token mới, Frontend cập nhật vào biến RAM (In-Memory), sau đó giải phóng hàng đợi và tự động gửi lại request ban đầu với Access Token mới. Người dùng hoàn toàn không hề nhận biết được phiên vừa được làm mới.

### Câu 3: *Nếu Access Token vẫn còn 10 phút hiệu lực nhưng tài khoản của User vừa bị Admin khóa (Banned) thì làm sao ngăn chặn ngay lập tức?*
* **Trả lời chuẩn:**
  Có 2 phương án tùy theo mức độ nhạy cảm của hệ thống:
  1. **Chấp nhận độ trễ tối đa 10 phút:** Với các hệ thống thông thường, ta chỉ cần xóa phiên Refresh Token trên Redis. Sau 10 phút khi Access Token hết hạn, user sẽ không thể refresh được nữa và bị đá văng ra ngoài.
  2. **Chặn tức thì (Instant Invalidation):** Đối với các API tài chính hoặc giao dịch tiền bạc quan trọng, bên cạnh việc verify chữ ký JWT, Auth Guard sẽ kiểm tra nhanh một key cờ trạng thái `user_status:<userId>` trên Redis (tốn dưới 0.5ms). Nếu trạng thái là `BANNED`, lập tức chặn đứng request dù Access Token vẫn còn hạn.

### Câu 4: *Trình bày sự khác biệt giữa hai thuật toán ký JWT: HS256 và RS256. Khi nào nên dùng loại nào?*
* **Trả lời chuẩn:**
  * **`HS256` (Symmetric - Khóa đối xứng):** Cả phía tạo token (Auth Service) và phía xác thực token (Resource API Service) đều phải dùng chung một `SECRET_KEY`.
    * *Khi nào dùng:* Phù hợp với kiến trúc Monolith hoặc khi tất cả các service nội bộ đều nằm trong cùng một mạng bảo mật và tin tưởng lẫn nhau.
  * **`RS256` (Asymmetric - Cặp khóa bất đối xứng):** Auth Service sử dụng **Private Key** bí mật để ký token; các Resource Service khác chỉ cần giữ **Public Key** để giải mã và kiểm tra tính hợp lệ.
    * *Khi nào dùng:* Bắt buộc trong kiến trúc Microservices phân tán lớn, hoặc khi hệ thống của bạn cung cấp SSO (Single Sign-On) / OAuth2 cho các ứng dụng của đối tác bên thứ ba (Third-party clients). Đối tác chỉ cần lấy Public Key từ endpoint `.well-known/jwks.json` để verify mà không có nguy cơ làm lộ Private Key tạo token.
